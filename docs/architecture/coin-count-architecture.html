Coin Count multiplayer backend

How up to 20 concurrent players join a shared game, get their own coins to count, and pool every correct guess into one running total — built entirely on Firebase (Auth, RTDB, Cloud Functions, Hosting).

System diagram

client ↔ functions ↔ RTDB
function-mediated write (authoritative)
client-direct write (presence only)
realtime read, fanned out to every client

Why it's shaped this way

Cloud Functions own every state change

A player's guess and the shared total are both things every other player sees live. If clients wrote guesses straight to RTDB, two correct answers landing in the same tick could race and undercount totalMoney, or a slow client could show a stale coin count after someone else's turn resolved. Routing writes through a callable function that runs an RTDB transaction removes that class of bug — exactly the client-sync inconsistency this project is already trying to avoid.

Presence stays client-direct

onDisconnect() only exists on the client SDK's live connection — a Cloud Function can't register "remove me if I vanish" on someone else's socket. So leaving (including tab close, crash, or network drop) is the one write a client makes directly, and it can only ever delete that client's own player node, which is why a compromised or buggy client can't use this path to touch anyone else's state or the shared total.

Join → play → leave

happy path
  1. Sign in. On load, the client signs in anonymously with Firebase Auth and receives a uid.
  2. Join. The client calls joinGame(). The function runs an RTDB transaction on /games/{gid}/players: if fewer than 20 players are present, it adds the player and hands them their first coin count; otherwise it returns room-full.
  3. Watch. The client subscribes to /games/{gid}/roster and /games/{gid}/totalMoney with onValue() — every join, leave, and correct guess from any player appears without a refresh.
  4. Guess. The player submits a count. submitGuess() checks it against the coin count stored server-side; if correct, one transaction adds that amount to totalMoney and writes the player a new problem.
  5. Leave. The client's own onDisconnect().remove(), registered at join time, fires automatically on tab close, crash, or network loss — no explicit "leave" call needed.

RTDB schema

/games/{'{'}gid{'}'}
// one active game room, up to 20 players { "players": { "{uid}": { "joinedAt": 1735000000000, "coinsPresented": 7, // this player's current problem "lastResult": "correct" // drives per-player feedback UI } // ...up to 20 uid entries }, "totalMoney": 482, // every correct guess, from every player, ever "roster": { // denormalized for a cheap join/leave listener "{uid}": true } }

Cloud Functions

callable
FunctionTriggerDoes
joinGame callable Transacts on players count vs. the 20-player cap; assigns a starting coin count.
submitGuess callable Compares the guess to the server-held count; on a match, transacts totalMoney += coinsPresented and calls newProblem.
newProblem internal Generates the next coin count for one player and writes it to their node.
onPlayerRemoved RTDB trigger Fires on players/{'{uid}'} delete (from onDisconnect); keeps roster in sync.

Out of scope, on purpose

No chat, profiles, or player-to-player messages exist in this design, and score manipulation isn't defended against — the game has no anti-cheat or hardened validation yet, matching the project's current threat model. The Cloud Functions layer above exists to keep honest clients in sync, not to stop dishonest ones.
